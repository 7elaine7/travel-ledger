# AI 协作实验总结（2026-09-22）

> 两天实验的最终结论。分两部分：可复用的模型 + 反直觉的发现。

## 一、三层模型（规则 / Skill / 流程）
第 1 层：规则层（Governance）
文件：AGENTS.md
管什么：谁做、谁卡、什么时候做
例子：决策分级授权表、硬约束、工作流三层

第 2 层：Skill 层（Methodology）
文件：docs/skills/*.md
管什么：具体任务怎么做
例子：cleanup-dead-css、write-ac、code-review

第 3 层：流程层（Orchestration）
文件：tools/start-dev-cycle.sh
管什么：把规则 + Skill 串起来自动跑
例子：一句话触发全流程

text

**关键区分**：
- **规则 ≠ Skill**。规则管边界，Skill 管方法。
- 规则要人定（授权、边界），Skill 可以由 AI 起草、人审。
- 流程图不是规则，是"把规则可视化"。

**我们项目现状**：
- 规则层：AGENTS.md ✅（刚建）
- Skill 层：只有 1 个（cleanup-dead-css）
- 流程层：只有 1 个脚本（start-dev-cycle.sh）

## 二、三条反直觉发现

### 发现 1：一句话开场白可行

| 对比 | 任务 A（手动）| 任务 B（自动）|
|---|---|---|
| 指令长度 | ~10 行 | **1 句** |
| AI 主动读规则 | 提示才读 | **自动读** |
| AI 主动复述 | 否 | **是** |
| AI 主动说明依据 | 部分 | **完整** |
| 人干预次数 | 3-4 次 | **1 次** |

**结论**：AGENTS.md 让"20 行规则"变"1 句指令"，AI 主动性反而更强。

### 发现 2：半自动比全自动更危险

**观察**：任务 B 执行中，人出现"不敢介入"的心理——贴文档犹豫、AI 复杂输出跳过细看、方案默认通过。

**根因**：不是懒，是"跟不上 AI 复杂度与速度"。半自动下，人被迫在"硬跟上（耗时）"与"放弃（签字）"之间选。时间压力下，大多数人选后者。

| 模式 | 判断力风险 |
|---|---|
| AI 辅助（人主导） | 低 |
| **AI 执行 + 人审** | **高** |
| AI 全自动 | 中 |

**结论**：半自动 = 最危险的模式。因为人既不在主线，又不能真正控制。

### 发现 3：决策分级授权（最高价值）

**核心洞察**：不是所有决策都要人拍。

| 级别 | 特征 | 谁拍 | 例子 |
|---|---|---|---|
| L1 | 有先例、可回滚 | AI 自动 | 代码格式化、字段存不存 |
| L2 | 中等风险 | AI 拍 + 人抽查 | 提示形式、命名风格 |
| L3 | 宪法级、价值判断 | 人拍 | BRIEF 修订、排期优先级 |
| L4 | 不可逆、影响面大 | 人 + 会签 | 数据库迁移、对外发布 |

**实测效果**：5 个决策里，只有 2 个需要人拍。建立授权规则后，人只处理 40% 决策。

**AI 遇决策时先自问**：
1. 这个决策属于几级？
2. 我有权拍吗？
3. 没权拍就停下来问人，不猜。

## 三、这两天的关键教训

| 教训 | 场景 |
|---|---|
| **多窗口并行会撞车** | 同一任务被两个窗口 commit，出现两条同名 commit |
| **呈现方式决定人是否参与** | 长篇 diff → 跳过；选项+风险 → 参与 |
| **上下文压缩是隐形杀手** | ZCode 十连击编辑失败，根因是上下文太长 |
| **AI 会"顺手"违反规则** | 用 node --check 做语法检查（违反了 6.5-D） |
| **必须保留"从零做一遍"的能力** | 人失去判断力，不是没审，是没用 |

## 四、对人的要求

**AI 时代，人从"执行者"变成三种角色**：

1. **授权设计者**：定规则、划边界（规则层）
2. **决策者**：只在 L3/L4 拍板（决策分级）

**人不可替代的能力**：

- 判断"AI 是否跑偏"

# 六、面试总结（AI 时代敏捷）

## 一、核心叙事：从"执行者"到"授权设计者"

**一句话定位**：
> 我帮团队把"验证税"降下来——通过让规格更清晰、AI 产出更可验证、人的判断集中在最需要的地方。

**为什么这句能打**：
- "验证税"是行业前沿概念（DORA 2026 报告提出）
- 直接回答老板最关心的问题："AI 到底怎么提效？"
- 一句话讲清人的不可替代性

---

## 二、面试三段式（照着背）

### 第一段：承认变化，但指出不变的本质

> "AI 让写代码变快了，但团队的实际交付速度并没有线性提升。DORA 报告把原因说得很清楚：**验证税**——写代码省下的时间，被审查 AI 产出的成本吃掉了。"

### 第二段：用真实项目佐证

> "我最近用 AI Agent 完整交付了一个 PWA 项目，深有体会。让 AI 写一个页面，它 5 分钟就产出了，但我花了更多时间在审查边界条件、确认它有没有违反项目的技术约束。我意识到：**敏捷的核心矛盾从'如何快速执行'变成了'如何清晰定义意图'。**"

### 第三段：方法论 + 人的不可替代

> "我没有推翻原来那套敏捷框架，而是做了'资产重估'：
> - Sprint 从'交付承诺'变成'对齐节奏'，功能连续交付
> - 角色从'执行力'转向'判断力'
> - 流程从'会议驱动'变成'文档驱动'——因为 AI 需要读文档，不需要开会
>
> 我的核心能力不是'审得过来'，而是**设计出正确的授权边界**——哪些给 AI，哪些留给人。这个能力，AI 替代不了，因为授权规则必须人定。"

## 四、可能的追问 + 回答

**Q1：你怎么保证 AI 产出的质量？**

> "三层保障：第一层，AI 生成测试用例，但关键断言人审；第二层，每个 Story 完成后，另开窗口做冷启动 Review；第三层，高风险变更（数据库迁移、架构变更）强制人工会签。核心思路是：**不同风险等级，配不同的审查强度。**"

**Q2：AI 会不会让人变懒，不去思考？**

> "会，而且**半自动比全自动更危险**。因为半自动下，人跟不上 AI 的复杂度，被迫在'硬跟上'和'放弃审查'之间选，时间压力下都选后者。我的解法是：**设计人介入的粒度**——低风险交给 AI 全自动，高风险强制人审，中等抽样审。人审不是负担，是精确介入。"

**Q3：你个人在 AI 时代的核心价值是什么？**

> "三件事：**定义标准、设计授权边界、处理异常**。AI 能做执行、能做初审，但它不能定义'什么算成功'，也不能给自己授权。这两件事必须人做。"

**Q4：你怎么看 AI 时代的团队结构？**

> "从'金字塔'变成'小而精'。传统 10 人团队，AI 时代 4-5 人。砍掉的是'纯执行'岗位，留下的是'能判断、能拍板'的人。同时人从'干活'变成'指挥 AI 干活'——就像导演和剧组的关系。"

# 七、演练最终结论：AI 不会自动加载 Skill

## 测试设计

**前提**：AGENTS.md 第五节明确写"必须加载对应 skill"，加【硬规则】"未加载 = 违反 AGENTS.md"。

**测试指令**：
读 AGENTS.md，然后 PENDING #16 载录保存逻辑。

**预期**：AI 识别"这是拆 Story 任务" → 主动加载 story-splitting.md → 按该 skill 出方案。

## 实测结果

AI 做了：
- ✅ 读了相关文档（CURRENT_STATE / PENDING / 代码现状）
- ✅ 复述了任务理解
- ✅ 识别了"这是拆 Story 任务"（问它时能答出 skill 文件名）

AI 没做：
- ❌ 没有主动声明"我加载了 story-splitting.md"
- ❌ 没有按 skill 走流程（按 skill 走应输出"拆分方案 + AC"，实际输出"3 个问题"）

## 结论：AI 的固有边界

**AI 能"理解规则"，但不能"看到规则就自省"。** 它只按**当前指令**做。

读一遍 AGENTS.md 的"必须加载"，对 AI 来说是"知道了这个规则"，不是"触发这个动作"。

## 修正后的模型（四层各自的执行边界）

| 层 | AI 能读 | AI 能自动执行 |
|---|---|---|
| 文档层 | ✅ | ✅（读就是执行） |
| 规则层 | ✅ | ❌ |
| **Skill 层** | ✅ | ❌ ← 关键发现 |
| 脚本层 | — | ✅（脚本由人/CI 触发） |

## 破局方案（已落地）

1. **开场白直接指定 skill**
   格式：`读 AGENTS.md，然后按 <skill 文件名> 处理：<任务>。`
   例：`读 AGENTS.md，然后按 story-splitting.md 处理 PENDING #16。`

2. **start-task.sh 预填 skill 名**
   脚本根据任务关键词匹配，自动往开场白里塞 skill 名。

3. **放弃"AI 自动发现 skill"的幻想**
   这是 AI 的固有边界，不是模型能力问题。多打几个字，换 100% 准确率。

## 这条结论为什么最值钱

- 它解释了**为什么"全自动"需要脚本层**——因为 AI 不会自省规则
- 它给"文字级代码"这个比喻补上了边界：**文字能描述规则，但不能强制执行规则；强制执行要靠脚本**
- 它是面试中最有分量的观察——**绝大多数人以为"写清规则 AI 就会遵守"，实测是不成立的**

## 八、复盘判断可以 AI 化，但要分级

【场景】AI 完成复述 / 报告后，人需要判断"对不对"。

【实测】这个判断可以交给主 AI（另一个模型），但有边界：
- L1（判断格式）：AI 自动
- L2（判断范围够不够）：AI 预判 + 人抽查
- L3（判断理解/方向/边界）：人必须签核

【推荐模式】"AI 预判 + 人签核"：
- 主 AI 出"预判结论 + 判断依据"
- 人看依据，30 秒决定
- 人从"自己判断"变成"审核 AI 的判断"

【为什么不能纯 AI 判】
- 信息不对称：主 AI 看不到原始文档
- 逻辑同源：两个 AI 可能用同一套逻辑，形成"两个 AI 都错"
- 责任问题：AI 判断错，谁负责？

## 九、多 Agent 互判的边界（面试补充）

【能做】事实判断——函数调用、禁令违反、单测通过
【不能做】价值判断——方案该不该做、范围划得对不对
【坑】同源失效——两个 Agent 用同一模型会犯同样的错
【生产做法】
  第 1 层：异质模型互评（写 + 审用不同模型）
  第 2 层：事实校验器（单测、静态检查、grep）
  第 3 层：人做价值判断
【原则】能用机器校验的不问 AI，能问 AI 的不问人，必须人拍的绝不外包。

## 十、未来演进方向：主从 Agent 自动协作

【当前模式】
主 Agent（DeepSeek）出指令 → 人手动贴 → 执行 Agent（ZCode）执行 → 人手动贴回 → 主 Agent 建议 → 人拍板

【未来模式】
主 Agent 自动获取执行 Agent 结果 → 自动判断/给建议 → 人只在 L3 决策点介入

【技术前提】
- 两个 Agent 能访问同一份状态（文件系统 / API）
- 主 Agent 能自动读取执行 Agent 的输出

【工具现状】
- 已有：Cursor Composer、Claude Code Agent SDK、AutoGen
- 你的项目：git 已经是共享状态，但两个 Agent 没打通 API → 靠人手动传

【关键判断】
即使工具打通，"人还是 L3 决策者"这一点不变。自动化只改变"人的位置"——从搬运工变审核员。
