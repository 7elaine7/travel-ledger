# 实验二：JSON vs Markdown 状态管理对照实验

> 目的：验证 AI 协作中，状态文件用 JSON 还是 Markdown，对换窗口恢复、行为约束的影响。

---

## 一、实验设计

**背景**：项目中已有 Markdown 状态体系（CURRENT_STATE.md、PENDING.md、SPRINTS.md），想验证结构化 JSON 是否恢复更快、约束更强。

**对照维度**：

| 组 | 状态形式 | 说明 |
|----|---------|------|
| A 组 | Markdown 分散文件 | 状态散在多个 .md 里 |
| B 组 | JSON 结构化文件 | 状态集中在一个 .json 里 |

**实验任务**：同一任务（拆分 Sprint 4 计划），跑完后新窗口复述状态。

**测量**：读取文件数、答案完整度、AI 行为合规性、恢复成本。

---

## 二、逐组观察

### A 组（Markdown）

| 项 | 内容 |
|----|------|
| 读取文件 | 4 个主项目文件 + git log + ls + 搜索 |
| 答案完整度 | 100% |
| 是否需要人提示 | 不需要，自己找全 |
| 恢复方式 | 多文档交叉验证 |
| 状态来源 | 原生分散在多个 .md |
| AI 行为合规 | 全程零工具绕过 |

### B 组（JSON）

| 项 | 内容 |
|----|------|
| 读取文件 | 2 个实验文件（JSON + 输出） |
| 答案完整度 | 100% |
| 是否需要回主项目 | 需要——JSON 本身缺上下文，必须回读 SPRINTS.md 补 |
| 恢复方式 | JSON 为主，回头读主项目补上下文 |
| 状态来源 | 需先"搬运"进 JSON |
| AI 行为合规 | 三次尝试用工具（python3、git status），被权限弹窗拦住 |
| 关键行为 | 自述"这不是我新拆的方案，是从主项目忠实表示过来的" |

### 汇总对比

| 指标 | A 组（Markdown） | B 组（JSON） |
|------|-----------------|-------------|
| 工具绕过尝试 | 0 次 | 3 次（python3 + git status） |
| 是否读 AGENTS.md | 是 | **否**（开头声称读了，实际没读） |
| 复述读文件数 | 4 个主项目文件 | 2 个实验文件（但信息已提前搬运） |
| 复述答案完整度 | 100% | 100% |
| 信息原生承载 | 是 | 否（需先搬运） |
| 主动发现 | PENDING 重复行、SPRINTS 缺行 | 路径错误、未碰主项目 |

---

## 三、核心发现

### 发现 1：JSON 管字段约束，Markdown 管上下文

**JSON 的优势**：字段约束强。AI 只能改 `status` 和 `plan`，不能改 `constraints`、`task_name` 等其他字段。

**JSON 的劣势**：本身不承载上下文。AC 是上一轮从 SPRINTS.md 搬运进来的，JSON 原始文件里根本没有。换句话说——**JSON 是"被喂"了上下文，才具备恢复能力。**

**Markdown 的优势**：原生承载上下文。决策记录、为什么这么做、历史沿革，全在里面。

**Markdown 的劣势**：恢复成本高，需要读 4 个文件 + git log 交叉验证。

### 发现 2：AI 只遵守它实际读到的约束

B 组 AI 开头声称"按 AGENTS.md 的开工流程做"，但实际没读 AGENTS.md 文件。

结果：出现三次工具绕过。

**对比 A 组**：读了 AGENTS.md，全程零绕过。

**结论**：AI 只遵守它实际读到的约束，声明不等于执行。这是"加载"问题，不是"格式"问题。

### 发现 3：约束形式决定遵守度

| 约束形式 | 遵守情况 |
|---------|---------|
| JSON 字段约束（只能改 status/plan） | 完全遵守 |
| AGENTS.md 全局禁令（禁止工具） | 未读 → 绕过 |

**结构化字段约束的遵守度，高于自然语言行为禁令。**

这不是"格式之争"，是"加载之争"。JSON 文件它读了，所以生效；AGENTS.md 它没读，所以失效。

---

## 四、结论

**三种格式各管一段，不是替代关系**：

| 格式 | 管什么 | 适用场景 |
|------|--------|---------|
| AGENTS.md | 全局行为约束 | 每次开工必读 |
| Markdown | 上下文叙事 | 决策记录、历史沿革、项目状态 |
| JSON | 结构化状态字段 | 执行状态、多 Agent 对接、机器校验 |

**行业**：Harness 管行为 + Playbook 管流程 + todo.json 管状态。三种并存。

**落到本项目**：
- AGENTS.md 管行为 → 保留
- CURRENT_STATE.md / SPRINTS.md / PENDING.md 管上下文 → 保留
- 未来如需多 Agent 对接状态，可引入 JSON 管执行状态字段

---

## 五、实验局限

1. 只跑了一个任务，样本小
2. B 组 JSON 是人为构造的（从主项目搬运），不是自然沉淀的结果
3. 未量化"恢复成本"（读文件数、耗时），只有定性观察
4. 未验证"JSON + Markdown + AGENTS 三者组合使用"的效果

---

## 六、一句话总结

**JSON 不是"更好的状态管理"，它是"更严格的字段容器"。**

**三者互补：AGENTS.md 管行为，Markdown 管上下文，JSON 管状态字段。**

**核心发现**：AI 只遵守它实际读到的约束——不是格式决定遵守度，是加载决定遵守度。
