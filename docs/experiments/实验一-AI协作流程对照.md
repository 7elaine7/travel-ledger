# 实验一：AI 协作流程对照实验（2026-09-22）

> 目的：验证 AI 协作中，规则文件能否让「一句话开场白」替代「多行指令」，以及全自动/半自动/人工三种模式的差异。

---

## 一、实验设计

**对照维度**：同一类任务，手动指令 vs 自动指令（依赖 AGENTS.md）。

**变量**：
- A 组：手动贴 10 行规则
- B 组：一句话开场白，让 AI 自己读 AGENTS.md

**测量**：指令长度、AI 是否主动读规则、是否主动复述、人干预次数、耗时、产出质量。

**三个任务**：
- 任务 A：清理 PENDING #14 死 CSS（手动指令）
- 任务 B：修 PENDING #18 话筒图标 pointer-events（1 句话指令）
- 任务 C：出「PENDING #16 拆 Story」计划（方案类任务）

---

## 二、三个任务的详细记录

### 任务 A：手动跑通（清理 PENDING #14 死 CSS）

**时间线**：
- 写指令 + 发指令：5 分钟
- ZCode 执行：约 8 分钟
- 验收、commit、文档更新：待填

**执行结果**：
- 净删 163 行 / 3231 字节（两轮合计）
- 花括号配平 106/106
- 只改了 `css/styles.css` 一个文件
- commit: `06f3fbf`

**ZCode 主动发现的问题（5 个，全部超出指令范围）**：

| # | 发现 | 决策 |
|---|------|------|
| 1 | PENDING #14 描述错误——`.onboard-title` 仍被错误视图引用 | 保留 + 修正描述 |
| 2 | mock/s2-01 和 s2-02 引用了被删的 `.profile-btn` | 接受 |
| 3 | toast 注释变陈旧（引用了已删规则） | 顺手改 |
| 4 | 又扫出 3 条同类死样式（.home-card/.hello/.field-error） | 一起删 |
| 5 | 新发现 `.topbar`/`.topbar__app` 也是死样式 | 记 PENDING，留下批 |

**关键观察**：

ZCode 不只执行，还：
- 主动纠正了指令里的错误
- 主动报告了指令没覆盖的场景
- 主动扫出了同类问题
- 主动识别出陈旧注释

**对「自动化」的启示**：好的自动化不是「AI 严格按指令做」（那是脚本），而是：
- AI 能发现指令中的错误（人犯错时 AI 兜底）
- AI 能识别指令外的风险（人漏考虑时 AI 报警）
- AI 能给出改进建议（不盲目执行）

---

### 任务 B：自动跑通（PENDING #18 话筒图标 pointer-events）

**指令**（仅 1 句话）：

> 读 AGENTS.md，然后修 PENDING #18 话筒图标 pointer-events。

**ZCode 的自动行为（超预期）**：

1. 主动读了 AGENTS.md + 6.5-D + CURRENT_STATE（没提示，自动做）
2. 主动复述任务理解 + 改动点 + 不改的东西（等确认）
3. 主动找到依据（同文件 `.input-svg`/`.btn-bg` 已是同写法）
4. 主动说明越界（"PENDING #18 原状态写待 S1-03 处理，你这条指令等于提前修"）
5. 主动查缓存（提示"若点不动先硬刷，可能旧 CSS"）

**总结**：任务 B 用 1 句话，人干预 1 次，耗时减半，产出质量不变。但引出了一个新问题——多窗口撞车。

**新发现的问题：多窗口撞车**

任务 B 出现两条同名提交：
- `01b868d` — css 的 1 行改动（人手动 commit）
- `62d47a6` — PENDING 归档（ZCode commit）

**根因**：两个窗口并行操作，撞车。不是 bug，是自动化协作里的新协调问题。

**这个发现说明**：
- AI 越自动，「多线并行」就越常见
- 人从「执行者」升级为「交通指挥」——协调谁在什么时候做什么
- 这正是 AI 时代 PM 的核心新价值

---

### 任务 C：方案类任务的自动化（测试 AGENTS.md 上限）

**指令**：

> 读 AGENTS.md，然后出一份「如何把 PENDING #16 拆成 Story」的计划。

**ZCode 的自动行为**：

1. 自动读了 6 个文档（超预期，预期 3 个）：AGENTS.md、BRIEF 6.5-D、CURRENT_STATE、PENDING、SPRINTS、DESIGN_SPEC
2. 自动核对代码现状（发现载录页是全静态表单，范围比「接个保存」大）
3. 主动发现 2 处文档滞后（S3-09 引用错位、CURRENT_STATE 滞后）
4. 给出 3 个 Story 拆分 + 顺序建议 + 依赖关系
5. 列出 5 个需拍板的决策 + 每个的依据

**关键观察：呈现协议得到验证**

ZCode 输出里，5 个决策全部按「选项 + 依据 + 风险」格式给出——这正是「让人参与决策的形态」，而不是「展示 AI 能力的形态」。

**对照**：
- 差呈现：500 行 diff → 人看不懂 → 跳过
- 好呈现：3 个选项 + 优劣 + 风险 → 人能选 → 参与

**结论**：AGENTS.md 不止对「执行类任务」有效，对「方案类任务」也有效。人从「写方案」变成「审方案」，负担大幅下降。

## 四、实验结论

### 结论 1：一句话开场白可行

AGENTS.md 让「20 行规则」变「1 句指令」，AI 主动性反而更强。

### 结论 2：半自动比全自动更危险

**观察**：任务 B 执行中，人出现「不敢介入」的心理——贴文档犹豫、AI 复杂输出跳过细看、方案默认通过。

**根因**：不是懒，是「跟不上 AI 复杂度与速度」。半自动下，人被迫在「硬跟上（耗时）」与「放弃（签字）」之间选。时间压力下，大多数人选后者。

| 模式 | 判断力风险 |
|------|-----------|
| AI 辅助（人主导） | 低 |
| AI 执行 + 人审 | 高 |
| AI 全自动 | 中 |

**结论**：半自动 = 最危险的模式。因为人既不在主线，又不能真正控制。

### 结论 3：决策分级授权

**核心洞察**：不是所有决策都要人拍。

| 级别 | 特征 | 谁拍 | 例子 |
|------|------|------|------|
| L1 | 有先例、可回滚 | AI 自动 | 代码格式化、字段存不存 |
| L2 | 中等风险 | AI 拍 + 人抽查 | 提示形式、命名风格 |
| L3 | 宪法级、价值判断 | 人拍 | BRIEF 修订、排期优先级 |
| L4 | 不可逆、影响面大 | 人 + 会签 | 数据库迁移、对外发布 |

**实测效果**：任务 C 的 5 个决策里，只有 2 个需要人拍。建立授权规则后，人只处理 40% 决策。

### 结论 4：三层模型

| 层 | 文件 | 管什么 |
|----|------|--------|
| 规则层 | AGENTS.md | 谁做、谁卡、什么时候做 |
| Skill 层 | docs/skills/*.md | 具体任务怎么做 |
| 流程层 | tools/*.sh | 把规则 + Skill 串起来自动跑 |

**关键区分**：
- 规则管边界，Skill 管方法
- 规则要人定，Skill 可以由 AI 起草、人审
- 流程图不是规则，是「把规则可视化」

### 结论 5：自动化没有减少决策负担

自动化只是把决策从「执行」转到「监督与协调」。AI 主动纠错，反而增加「人要做决策」的次数。

## 五、关键教训

| 教训 | 场景 |
|------|------|
| 多窗口并行会撞车 | 同一任务被两个窗口 commit，出现两条同名 commit |
| 呈现方式决定人是否参与 | 长篇 diff → 跳过；选项+风险 → 参与 |
| 上下文压缩是隐形杀手 | ZCode 十连击编辑失败，根因是上下文太长 |
| AI 会「顺手」违反规则 | 用 node --check 做语法检查（违反 6.5-D） |
| 必须保留「从零做一遍」的能力 | 人失去判断力，不是没审，是没用 |

## 六、附加发现

### 发现 A：AI 不会自动加载 Skill

**测试设计**：

前提：AGENTS.md 第五节明确写「必须加载对应 skill」，加【硬规则】「未加载 = 违反 AGENTS.md」。

测试指令：读 AGENTS.md，然后 PENDING #16 载录保存逻辑。

预期：AI 识别「这是拆 Story 任务」→ 主动加载 story-splitting.md → 按该 skill 出方案。

**实测结果**：

AI 做了：
- 读了相关文档（CURRENT_STATE / PENDING / 代码现状）
- 复述了任务理解
- 识别了「这是拆 Story 任务」（问它时能答出 skill 文件名）

AI 没做：
- 没有主动声明「我加载了 story-splitting.md」
- 没有按 skill 走流程

**结论：AI 的固有边界**

AI 能「理解规则」，但不能「看到规则就自省」。它只按当前指令做。

| 层 | AI 能读 | AI 能自动执行 |
|----|--------|--------------|
| 文档层 | 是 | 是 |
| 规则层 | 是 | 否 |
| Skill 层 | 是 | 否 |
| 脚本层 | — | 是（脚本由人/CI 触发） |

**破局方案**：
1. 开场白直接指定 skill
2. start-task.sh 预填 skill 名
3. 放弃「AI 自动发现 skill」的幻想

**核心结论**：文字能描述规则，不能强制执行规则；强制执行要靠脚本。

### 发现 B：多 Agent 互判的边界

| 类型 | 能不能做 |
|------|---------|
| 事实判断（函数调用、禁令违反、单测通过） | 能做 |
| 价值判断（方案该不该做、范围划得对不对） | 不能做 |

**坑**：同源失效——两个 Agent 用同一模型会犯同样的错。

**生产做法**：
- 第 1 层：异质模型互评（写 + 审用不同模型）
- 第 2 层：事实校验器（单测、静态检查、grep）
- 第 3 层：人做价值判断

**原则**：能用机器校验的不问 AI，能问 AI 的不问人，必须人拍的绝不外包。

### 发现 C：复盘判断 AI 化的边界

| 级别 | 判断类型 | 谁做 |
|------|---------|------|
| L1 | 判断格式 | AI 自动 |
| L2 | 判断范围够不够 | AI 预判 + 人抽查 |
| L3 | 判断理解/方向/边界 | 人必须签核 |

**推荐模式**：「AI 预判 + 人签核」。

**为什么不能纯 AI 判**：
- 信息不对称
- 逻辑同源（两个 AI 可能用同一套逻辑，都错）
- 责任问题

## 七、未来演进：主从 Agent 自动协作

**当前模式**：
主 Agent（DeepSeek）出指令 → 人手动贴 → 执行 Agent（ZCode）执行 → 人手动贴回 → 主 Agent 建议 → 人拍板

**未来模式**：
主 Agent 自动获取执行 Agent 结果 → 自动判断/给建议 → 人只在 L3 决策点介入

**技术前提**：
- 两个 Agent 能访问同一份状态
- 主 Agent 能自动读取执行 Agent 的输出

**关键判断**：
即使工具打通，「人还是 L3 决策者」这一点不变。自动化只改变「人的位置」——从搬运工变审核员。
