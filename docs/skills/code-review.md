# Skill: code-review

## 什么时候用
Story 完成后，人或 AI 说"做一次 review"时。

## 前置条件
- Story 的代码已 commit
- 人有时间读 Review 报告

## 步骤

### 1. 冷启动准备
- 新开一个窗口（不要用执行 Story 的窗口）
- 读 PROJECT_BRIEF.md 的 6.5 节（DoD 七条）
- 读 DESIGN_SPEC.md 的对应章节（如果 Story 涉及 UI）
- **不要读执行窗口的对话历史**（防止被影响判断）

### 2. 独立审查
- 从 git log 找到本 Story 的 commit
- git show <commit> 看完整改动
- 按下面的清单逐项检查

### 3. 检查清单
- [ ] 是否违反 BRIEF 禁令？（CDN / node / 未确认写库）
- [ ] 是否改了不该改的文件？（js/ 非授权改动）
- [ ] 是否有死引用？（grep 被删的 id/class）
- [ ] 单测是否覆盖新逻辑？
- [ ] 边界条件是否有防御？
- [ ] 错误路径是否有兜底？
- [ ] 命名是否一致？
- [ ] 注释是否过时？

### 4. 报告格式
Review 报告：<Story ID>
严重问题（必须修）
<问题> | 位置 <文件:行号> | 建议 <怎么改>

中等问题（建议修）
...

低优先级 / 观察
...

结论
□ 通过，可继续下一 Story
□ 有严重问题，修复后重审

### 5. 强制检查点
- 报告出完后，**等人确认**，不要自动改代码
- 人回复"修复"后，另开窗口修复（不要在执行窗口改）

## 已知陷阱
- **同窗口 review 会失效**：AI 会"自证对"，必须冷启动
- **报告太长人会跳过**：严重问题放最前，最多 5 条
- **不要 review 非本 Story 的改动**：范围外的问题另记 PENDING
