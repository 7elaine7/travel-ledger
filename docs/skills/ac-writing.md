# Skill: ac-writing

## 什么时候用
- 拆 Story 时（配合 story-splitting skill）
- 人给一个功能描述，需要 AI 帮忙写验收标准
- Review 时发现 AC 模糊

## 三条硬标准（每条 AC 必须满足）

### 标准 1：可 grep 验证
**反例**："系统应该快速响应"
**正例**："接口 P95 < 500ms"（可被日志/监控验证）

**判断法**：如果这条 AC 通过后，你不知道用什么命令验证它——就是模糊的。

### 标准 2：可单独测试
**反例**："用户能正常使用记账功能"
**正例**："用户输入'今天吃面20块'，点击保存，账簿页出现一条 ¥20 餐饮记录"

**判断法**：如果这条 AC 需要结合其他功能才能测——就要拆。

### 标准 3：无模糊词
**禁用词清单**：
- 合理、适当、尽快、快速、友好、流畅
- 大概、差不多、几乎、基本

**判断法**：把这些词划掉，AC 还能验证吗？不能——就要重写。

## 格式模板

```markdown
### AC-<编号>：<一句话描述>
- **前置**：<什么状态>
- **操作**：<用户做什么>
- **期望**：<系统返回什么>

**验证方式**：<手动步骤 or grep 命令 or 单测用例名>

完整示例：
### AC-1：保存后回首页
- 前置：载录页有有效四字段
- 操作：点击"缮录归帙"
- 期望：跳回首页，输入框清空

验证方式：
- 手动：Safari 操作，观察视图切换
- 代码：`switchTab('home')` 被调用

步骤
1. 收集输入
读 Story 范围（一句话）

读相关 DESIGN_SPEC 章节（涉及 UI 时）

读 PENDING/BACKLOG 里的原始需求

2. 拆出可验证的场景
按"用户视角"列出所有关键路径：

主流程（happy path）

边界（空值、最大值）

错误（非法输入、网络失败）

3. 逐条按三条硬标准写
写完每条自查：

□ 可 grep 验证？
□ 可单独测试？
□ 无模糊词？
4. 输出格式
markdown
## Story <ID> 的 AC

### AC-1：<描述>
...

### AC-2：<描述>
...

### 明确不做
- <不做什么，防止范围膨胀>
5. 强制检查点
AC 草案出来后，等人审

人审通过的才写进 SPRINTS.md

已知陷阱
AC 写成需求：AC 是"什么算对"，需求是"做什么"。别混。

AC 太笼统：一条 AC 塞了 3 个场景 → 拆成 3 条。

AC 太机械：每个按钮都要测一遍 → 只测关键路径。

忘了"不做"：不写"不做"，AI 会自由发挥 → 范围膨胀。

验证方式缺失：AC 写得对，但不知道用什么验证 → 等于没写。
