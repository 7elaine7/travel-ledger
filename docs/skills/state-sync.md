# Skill: state-sync

## 什么时候用
- 多步任务（3 步以上）开始时
- 人做完一步，说"X 完成"时
- 人机对话中怀疑"到底做没做"时

## 解决什么问题
人机状态不同步。三个典型场景：
1. 人只做了 1，来讨论 2 → AI 以为 123 都做了
2. 人全做了但忘说 → AI 重复派活
3. 讨论没完一段段发 → AI 丢上下文

## 规则 1：多步任务必须有状态文件

任何 3 步以上的任务，AI 先建 docs/tasks/<任务名>.md，内容格式：

    # 任务：<任务名>
    
    - [x] 步骤1：<描述>（完成时间）
    - [~] 步骤2：<描述>（进行中）
    - [ ] 步骤3：<描述>（未开始）

状态标记：[ ] 未开始 / [~] 进行中 / [x] 完成

## 规则 2：AI 开工前必须先查状态

不许凭对话记忆判断。按顺序查：
1. git log — 这件事有 commit 吗？
2. docs/tasks/<任务名>.md — 当前到哪步？
3. grep 代码 — 改动是否已存在？

三条都查完，再报告状态。

## 规则 3：讨论结论必须落档才算定案

- 讨论完 → 立刻写入对应文档
- 讨论没完 → 不改文档（防半成品入档）
- "我说了但没确认" ≠ 定案

## 规则 4：人做完必说，AI 必记

- 人做完后说"X 完成"
- AI 立即：
  1. 更新 docs/tasks/<任务名>.md 状态
  2. git status 确认改动
  3. 报告下一步

## 强制检查点
- 状态文件必须是人能看懂的自然语言，不是代码 diff
- 每次会话结束时，状态文件必须是"最新真相"
- 状态文件进 git（跟代码一起走）

## 已知陷阱
- 对话记忆不可信：长对话后 AI 会记错；只信文件
- 状态文件过期：人做了但没更新 → 每周 Retro 时核对一次
- 多个任务状态混乱：一个任务一个文件，不要混在一个文件里
